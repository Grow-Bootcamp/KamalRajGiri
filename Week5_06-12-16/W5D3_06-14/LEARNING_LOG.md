## 1. Express Error Handling

Express error handling was studied using global and route-specific approaches.

### Global Error Handling

A global error handler provides a centralized location for handling errors generated by routes, controllers, and services. This helps maintain a consistent response format across the application.

The global handler is responsible for:

- Receiving errors passed through Express middleware.
- Determining the appropriate HTTP status code.
- Returning a consistent error response.
- Handling unexpected application errors.
- Preventing duplicate error-handling logic in individual routes.

The error-handling middleware follows the Express error middleware signature:

```js
(err, req, res, next)
```

### Route-Specific Error Handling

Route-specific handling is useful when a route requires custom behavior for a particular failure, such as:

- A student record not being found.
- Invalid request data.
- A service operation failing.
- A request not satisfying a route-specific condition.

Expected errors can be passed to the next middleware using:

```js
next(error)
```

This allows the global error handler to process the error consistently.

## 2. Custom Application Errors

The `app-error.js` file provides a reusable application error structure.

A custom error class can contain information such as:

- Error message.
- HTTP status code.
- Error type or category.
- Operational error information.

Using a custom error structure allows controllers and services to create meaningful errors without directly constructing response objects.

Example error flow:

```text
Service error
    ↓
Controller passes error to Express
    ↓
Global error-handling middleware
    ↓
HTTP error response
```

This separates error creation from error response formatting.

### Benefits

- Consistent status codes.
- Reusable error objects.
- Cleaner controller and service code.
- Centralized response formatting.
- Easier debugging and maintenance.

### Related File

- `app-error.js`

## 3. Controller and Service Error Flow

The student functionality is separated into controller and service layers.

### Controller Responsibilities

The controller layer is responsible for:

- Receiving the Express request.
- Reading request parameters or body data.
- Calling the appropriate service method.
- Sending successful responses.
- Passing errors to the Express error middleware.

### Service Responsibilities

The service layer is responsible for:

- Containing student-related business logic.
- Performing the required operation.
- Returning successful results.
- Throwing or propagating errors when an operation fails.

This separation prevents business logic from being tightly coupled to Express request and response objects.

### Error Propagation

Errors generated in the service layer should be propagated to the controller and then passed to the global error handler. This creates a predictable error flow throughout the application.

## 4. Logging with Winston and Morgan

The application uses separate logging concepts for application events and HTTP requests.

### Winston

Winston is used for application-level logging. It can be used to record:

- Application errors.
- Service failures.
- Debugging information.
- Important runtime events.

A centralized logger configuration makes logging available across controllers, services, and other application modules.

### Morgan

Morgan is used for HTTP request logging. It records information related to incoming requests, such as:

- HTTP method.
- Requested URL.
- Response status.
- Request processing details.

### Winston and Morgan Responsibilities

| Logger | Purpose |
|---|---|
| Winston | Application events, errors, and runtime messages |
| Morgan | HTTP request and response logging |

Using both provides visibility into request activity and internal application behavior.

### Related File

- `logger.js`

## 5. Request Data Validation

Request validation was reviewed as a required step before business logic execution.

Validation should verify that incoming data:

- Contains the required fields.
- Uses the expected data format.
- Meets the required value constraints.
- Does not contain invalid or malformed values.

Invalid input should be rejected before it reaches the service layer and should return an appropriate client error response.

### Validation Flow

```text
Incoming request
    ↓
Validate request data
    ↓
Return client error if invalid
    ↓
Call controller and service logic
    ↓
Return successful response
```

### Benefits of Validation

- Prevents malformed data from reaching the service layer.
- Produces clearer client-side error responses.
- Reduces unexpected runtime failures.
- Improves API reliability.
- Protects business logic from invalid input.

## 7. Key Technical Learnings

- Express error middleware must use the four-argument signature.
- Global error handling centralizes application error responses.
- Route-specific errors can be forwarded using `next(error)`.
- Custom error classes make application errors reusable and structured.
- Controllers should handle HTTP concerns, while services should contain business logic.
- Winston is suitable for application-level logging.
- Morgan is suitable for HTTP request logging.
- Request validation should happen before business logic execution.
- Consistent error responses make APIs easier to consume and debug.
